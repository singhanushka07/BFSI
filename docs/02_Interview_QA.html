A. Project Overview & Motivation 6 Questions
1
Explain this project in 2 minutes — what it does, who it's for, and why it matters. Easy
What: A full-stack AI platform that automates financial risk assessment for corporations using 6 specialized AI agents (4 risk analysts + Devil's Advocate + Judge), a RAG pipeline, SSE real-time streaming, guardrails with hallucination detection, and a conversational risk chat — all delivered through a real-time analytics dashboard.

Who: Financial analysts, risk managers, and compliance officers at BFSI institutions (banks, insurance companies, investment firms) who currently spend hours manually reading annual reports, news, and regulatory filings.

Why it matters: Traditional risk analysis is manual, slow, and inconsistent across analysts. This platform reduces manual document analysis effort by ~80% by intelligently retrieving and reasoning over uploaded financial PDFs. It provides a unified, automated, reproducible risk score covering 4 dimensions simultaneously — with live SSE streaming of agent progress, GPT-validated guardrails to catch hallucinations, a multi-agent debate for adversarial verification, and an interactive chat to explore results conversationally.
Key talking point: "We went from a human reading 200-page annual reports to an AI agent querying the exact relevant paragraphs in seconds — streamed live, validated by guardrails, stress-tested by a Devil's Advocate agent, and explorable via chat."
2
What does BFSI stand for, and what are the specific risk domains you cover? Easy
BFSI = Banking, Financial Services, and Insurance.

The platform covers 4 risk domains, each handled by a dedicated AI agent:
• Market Risk — volatility, Value-at-Risk (VaR 95%), beta, P/E ratio, price history analysis
• Sentiment Risk — news headline analysis, positive/negative ratio, reputational risk, investor confidence
• Financial Report Risk — balance sheet analysis, liquidity (current ratio), leverage (D/E), profitability (ROE, ROA), powered by RAG over uploaded PDFs
• Regulatory Compliance Risk — checks against 8 frameworks: Basel III, AML/KYC, Dodd-Frank, GDPR, IFRS 9, SOX 404, MiFID II, PCI DSS
3
What is the "~80% reduction in manual analysis" claim based on? Medium
The 80% figure refers specifically to the financial document analysis phase — not the entire risk workflow.

Traditionally, an analyst reading a 200-page annual report to extract risk signals takes 3–5 hours. The RAG pipeline:
1. Chunks the PDF into ~150-word segments
2. Embeds and indexes all chunks in ChromaDB
3. At query time, semantically retrieves only the top-5 most relevant chunks (out of hundreds)
4. GPT-4o reasons over those ~750 words instead of 50,000

The analyst effort shifts from "read entire document" to "review AI-generated summary" — which is the 80% reduction. The remaining 20% is validation and judgment work that humans must still do.
Important: Be honest that this is a reasonable estimate for the document retrieval phase, not a measured production benchmark.
4
How is the overall risk score calculated? Walk me through the formula. Medium
The overall risk score is a weighted average of the 4 agent scores, implemented in the LangGraph aggregator node:

overall = (market × 0.30) + (sentiment × 0.20) + (financial × 0.30) + (compliance × 0.20)
Weight rationale:
• Market (30%) and Financial (30%) are given equal highest weight — quantitative, directly measurable
• Compliance (20%) — binary pass/fail nature means high impact but less gradient
• Sentiment (20%) — valuable but noisier signal due to media bias

Score ranges: 0–24 = LOW, 25–49 = MEDIUM, 50–74 = HIGH, 75–100 = CRITICAL

What makes this different from a simple spreadsheet with financial ratios? Medium
Four key differentiators:
1. Natural language reasoning: GPT-4o doesn't just compute ratios — it contextualizes them ("a D/E of 2.8 is concerning for a company with declining revenue and regulatory pressure")
2. Document understanding (RAG): A spreadsheet can't read a PDF. The RAG pipeline extracts risk signals from unstructured documents that contain qualitative risk disclosures
3. Multi-dimensional, simultaneous: 4 agents run in parallel conceptually, covering aspects that require different domain expertise
4. Reproducibility and auditability: Every analysis is stored in SQLite with full agent output, enabling trend analysis and historical comparison

What are the limitations of this platform? Hard
Being honest about limitations shows maturity:
• Mock data: Market data and news are simulated. A production version would need Yahoo Finance, Bloomberg, or NewsAPI integrations
• LLM hallucination (mitigated): GPT-4o can generate plausible-sounding but incorrect analysis. We now have guardrails (GPT-4o-mini validates each agent's output against MCP source data with confidence scores), but outputs still need human validation before trading decisions

Recently implemented features that addressed previous limitations:
• SSE real-time streaming: Agent results now stream live to the frontend via Server-Sent Events — no more waiting for all agents to finish
• Guardrails + hallucination detection: GPT-4o-mini validates each agent's output, returning confidence scores and flagged issues
• Conversational risk chat: Users can now chat with completed risk reports, asking follow-up questions with full analysis context
Always mention limitations proactively — interviewers respect self-awareness over overselling. But also highlight what you've already addressed.
B. AI / LangGraph / LangChain 12 Questions
7
Explain LangGraph. How is it different from just calling 4 functions in sequence? Medium
LangGraph defines agents as nodes in a compiled directed graph with a shared typed state (RiskState TypedDict). Key differences from plain function calls:

1. State typing: The state is strictly typed — each node knows exactly what fields it can read and write. Prevents accidental data corruption between agents.
2. Checkpointing: LangGraph can checkpoint state at each node, enabling pause-resume and debugging
3. Conditional routing: Edges can be conditional — e.g., "if market risk is CRITICAL, skip sentiment and go straight to regulatory"
4. Visualization: The graph can be rendered as a visual flow diagram for debugging
5. Built-in error handling: Node-level try/catch with state persistence means one agent failing doesn't crash the whole pipeline
workflow.set_entry_point("market_risk") workflow.add_edge("market_risk", "sentiment") workflow.add_edge("sentiment", "financial_report") workflow.add_edge("financial_report", "regulatory") workflow.add_edge("regulatory", "aggregator") workflow.add_edge("aggregator", "devils_advocate") workflow.add_edge("devils_advocate", "judge") workflow.add_edge("judge", END)
The graph now has 7 nodes: 4 risk analysts → aggregator → Devil's Advocate (challenges findings) → Judge (produces adjusted scores and final verdict).
8
What is a LangChain chain? Show a code example from your project. Easy
A LangChain chain is a composable pipeline: prompt | llm. The pipe operator (|) connects a prompt template to an LLM, passing the formatted prompt through to get a response.

prompt = ChatPromptTemplate.from_messages([ ("system", "You are an expert quantitative financial risk analyst."), ("human", "Analyze market risk for {company}. Volatility: {volatility}. VaR: {var_95}%.") ]) llm = ChatOpenAI(model="gpt-4o-mini", temperature=0.3) chain = prompt | llm response = chain.invoke({"company": "TechCorp", "volatility": "0.32", "var_95": "4.2"})
The temperature=0.3 makes responses more deterministic and professional — important for financial analysis.

What does the LangGraph RiskState TypedDict contain and why is typing important? Medium
class RiskState(TypedDict): company: str ticker: str sector: str collection_name: Optional[str] market_result: Optional[dict] sentiment_result: Optional[dict] financial_result: Optional[dict] regulatory_result: Optional[dict] final_report: Optional[dict] debate_result: Optional[dict] # Devil's Advocate challenge output judge_result: Optional[dict] # Judge verdict with adjusted scores error: Optional[str]
Why typing matters: TypedDict enforces that every node receives and returns the same shape of state. If the market agent returns a malformed dict, Python type checking catches it at compile time. The Optional fields start as None and get populated as each agent runs, making it easy to see which agents have completed.

New fields: debate_result holds the Devil's Advocate agent's challenges (identified weaknesses, contradictions, alternative interpretations). judge_result holds the Judge agent's verdict — which challenges are valid, adjusted risk scores, and overall confidence assessment.
10
Why temperature=0.3 for the LLM in financial agents? When would you use 0.0 or 1.0? Medium
temperature=0.3: Low enough to produce consistent, professional financial language without hallucination, but not zero — preserving natural variation in phrasing.

temperature=0.0: Fully deterministic. Use for structured output extraction (JSON parsing, classification, entity extraction) where the same input must always return the same output.

temperature=1.0: Creative, highly variable. Use for brainstorming, creative writing, marketing copy — never for financial analysis.

In our agents: 0.3 is the standard BFSI recommendation for "professional but not robotic" analysis text.
11
How does the Market Risk Agent calculate VaR (Value at Risk)? Hard
The platform uses the parametric VaR (variance-covariance method):

returns = [(closes[i] - closes[i-1]) / closes[i-1] for i in range(1, len(closes))] mean_return = sum(returns) / len(returns) std_return = sqrt(sum((r - mean_return)**2 for r in returns) / len(returns)) var_95 = abs(mean_return - 1.645 * std_return) * 100 # 95% confidence
1.645 = Z-score for 95% confidence (one-tailed normal distribution).

This means: with 95% probability, the daily loss will not exceed VaR%. A VaR of 4.2% means "we are 95% confident daily loss won't exceed 4.2% of portfolio value."

Limitation acknowledged: Parametric VaR assumes normally distributed returns — a known weakness for fat-tailed financial data. Historical simulation or Monte Carlo would be more robust in production.

What is the difference between LangGraph, LangChain, and LangSmith? Easy
LangChain: The base framework — prompt templates, LLM wrappers, output parsers, memory, tools, vector store integrations. The "building blocks."
LangGraph: Built on LangChain. Adds stateful, cyclical agent graphs. Enables multi-agent coordination, checkpointing, and conditional flows. The "orchestration layer."
LangSmith: Observability and tracing platform (SaaS). Not used in this project but would be added in production to trace every agent call, prompt, and token usage for debugging and cost monitoring.

Could you run the 4 agents in parallel instead of sequential? What are the trade-offs? Hard
Yes — LangGraph supports parallel node execution using add_edge from a fan-out node.

Parallel pros: 4x faster total execution time (from ~20s to ~5s)
Parallel cons:
1. The Financial Report Agent might benefit from the Market Agent's context (e.g., if volatility is extreme, financial risk weight should increase)
2. OpenAI rate limits — 4 concurrent GPT-4o calls may hit per-minute token limits
3. More complex error handling — a failure in one parallel branch needs to be isolated

Current design choice: Sequential was chosen for simplicity and the ability to pass intermediate results between agents (market result informs the aggregator's weighting). Parallel would be a production upgrade for the 4 risk agents once rate limiting is managed.

Important note on debate agents: The Devil's Advocate and Judge agents must run sequentially after the aggregator — they require the full aggregated risk report as input. The Devil's Advocate challenges findings based on the complete picture, and the Judge evaluates those challenges. This is inherently sequential: challenge → verdict. The 4 risk analysis agents could be parallelized, but the debate phase cannot.
Show you understand the trade-off, not just that parallel "is faster." Also explain why the debate phase is necessarily sequential.
13a
Explain the multi-agent debate mechanism — how do Devil's Advocate and Judge agents work? Hard
After the aggregator produces a unified risk report, the analysis enters the adversarial debate phase — two additional agents that stress-test the findings:

Devil's Advocate Agent: Receives the full aggregated report and systematically challenges it:
• Identifies weaknesses in reasoning (e.g., "the market risk score relies heavily on short-term volatility but ignores sector-wide downtrend")
• Finds contradictions between agents (e.g., "sentiment is positive but financial ratios show deteriorating liquidity")
• Proposes alternative interpretations of the same data
• Highlights data gaps or over-reliance on single sources

Judge Agent: Receives both the original report and the Devil's Advocate's challenges, then:
• Evaluates each challenge for validity — accepts, partially accepts, or dismisses
• Produces adjusted risk scores that account for valid challenges
• Generates a final verdict with a confidence level

LangGraph flow: market_risk → sentiment → financial_report → regulatory → aggregator → devils_advocate → judge → END

debate_result = { "challenges": [...], # List of identified weaknesses "contradictions": [...], # Cross-agent inconsistencies "alternative_views": [...] # Different interpretations } judge_result = { "verdict": {...}, # Per-challenge ruling "adjusted_scores": {...}, # Modified risk scores "confidence": 82, # Overall confidence (0-100) "reasoning": "..." # Judge's rationale }
The debate mechanism adds adversarial verification — similar to peer review in academia. It catches blind spots that a single-pass analysis misses.
13b
How does hallucination detection and guardrails work in the platform? Hard
Each agent's output is validated by a guardrails layer that uses GPT-4o-mini as an LLM-as-judge to detect hallucinations and verify factual consistency:

How it works:
1. After each risk agent completes, its output is sent to a separate GPT-4o-mini validation call along with the original MCP source data (market data, news, financial metrics, regulatory rules)
2. The validator checks: Does the agent's analysis accurately reflect the source data? Are any claims fabricated or unsupported?
3. Returns a confidence score (0–100) per agent and a list of flagged issues (specific statements that could not be verified against source data)

Trust score calculation: The overall trust score is a weighted average of individual agent confidence scores, using the same weights as the risk score formula (Market 30%, Sentiment 20%, Financial 30%, Compliance 20%).

Design decisions:
• Separate LLM call per agent: Isolates validation — one agent's poor output doesn't contaminate another's validation
• GPT-4o-mini (not GPT-4o): Validation is a simpler classification task — mini is sufficient and 10x cheaper
• Source data comparison: The validator compares against the actual MCP tool responses (raw data), not just the agent's prompt — this is what makes it a true hallucination check rather than just a coherence check
Guardrails reduce but don't eliminate hallucination risk. A trust score below 70 should trigger human review before decisions.

C. RAG Pipeline & ChromaDB 11 Questions
17
Explain the RAG pipeline end-to-end — from PDF upload to agent response. Medium
Step 1 — Upload: User POSTs a PDF via /api/rag/upload. FastAPI saves it to the uploads/ directory.
Step 2 — Parse: pypdf reads each page and extracts text. Pages are split into 150-word chunks with 20-word overlap.
Step 3 — Embed: OpenAI text-embedding-3-small converts each chunk to a 1536-dimensional vector.
Step 4 — Store: ChromaDB upserts the vectors + text + metadata (page number, source file) into a named collection.
Step 5 — Hybrid Retrieval: When the Financial Report Agent runs, it calls hybrid_rag_search(collection, query). This runs BM25 keyword search AND ChromaDB dense vector search in parallel, normalizes both score sets to [0,1], and combines them (60% dense, 40% BM25).
Step 6 — Re-ranking: The top-8 hybrid results are sent to GPT-4o-mini in a single batch prompt to score each chunk 0-10 for relevance. Top-4 are selected.
Step 7 — Reason: GPT-4o receives re-ranked chunks as context and generates a risk assessment grounded in document evidence.
17a
What is hybrid search and why is it better than pure dense vector search for financial documents? Hard
Dense search (ChromaDB) works by embedding the query into a vector and finding the closest stored vectors using cosine similarity. It excels at semantic meaning — "what is the liquidity risk?" → finds contextually similar text.

BM25 (sparse) search is a classic information retrieval algorithm that scores documents based on exact keyword frequency and inverse document frequency (IDF). It excels at precise terms.

Why hybrid wins for finance: Financial regulatory documents are full of precise terminology — "Basel III", "CET1 ratio", "SOX Section 404", "IFRS 9 Stage 2", "AML/KYC". Dense search may embed these terms into a general financial vector space and miss exact matches. BM25 retrieves them precisely as keyword matches.

Implementation: rag/hybrid_search.py uses rank_bm25.BM25Okapi. Both methods run on the same candidate set retrieved from ChromaDB, scores are min-max normalized, then linearly combined: score = 0.6 × dense + 0.4 × bm25. The alpha parameter (0.6) can be tuned per query type.
17b
Why use an LLM re-ranker instead of a cross-encoder model? What are the trade-offs? Hard
Cross-encoder models (like cross-encoder/ms-marco-MiniLM-L-6-v2) are the standard production re-ranker — they take (query, document) pairs and score relevance jointly, achieving high accuracy. However, they require ~80MB PyTorch model download and local inference overhead.

LLM re-ranking sends all candidates to GPT-4o-mini in a single batch prompt: "Score each chunk 0-10 for relevance to this financial risk query." It returns a JSON score array, chunks are sorted, and top-4 are selected.

Trade-offs:
• Cross-encoder pro: Faster (local), no API cost per re-rank, deterministic
• LLM re-ranker pro: No extra packages/model downloads, leverages GPT's financial domain knowledge, works out of the box with existing OpenAI integration
• LLM re-ranker con: Adds one API call, non-deterministic, cost per run

Design choice here: LLM re-ranking was chosen to avoid PyTorch dependency conflicts in the Python 3.12+ environment and to leverage GPT's deep understanding of financial regulatory language. Falls back to hybrid scores gracefully if the API call fails.
18
What is cosine similarity and why is it used for semantic search? Hard
Cosine similarity measures the angle between two vectors, not their magnitude:

cos(θ) = (A · B) / (|A| × |B|) → range: -1 (opposite) to 1 (identical)
Why for semantic search: Text embeddings encode semantic meaning as directions in high-dimensional space. "Debt risk" and "financial leverage" will have similar directional vectors even though they share no words — cosine similarity captures this semantic closeness.

vs. Euclidean distance: Euclidean distance is sensitive to vector magnitude (document length), which introduces noise. Cosine similarity normalizes for length — a short paragraph and a long paragraph about the same topic will still score high similarity.
19
Why chunk size 150 words with 20-word overlap? What happens with wrong chunk sizes? Hard
Too small (< 50 words): Chunks lose context — "revenue decreased" without knowing why. Embeddings become semantically thin. More API calls for embedding.
Too large (> 500 words): Chunks embed multiple topics, making the vector a blur. Retrieval becomes less precise — you get an entire section when you only needed one paragraph.
150 words: Fits one coherent "thought" — a paragraph about liquidity risk, or a disclosure about a specific regulatory matter. Produces focused, semantically sharp embeddings.
20-word overlap: Prevents context loss at boundaries. A sentence split across two chunks is captured by both, so the key fact is never lost. Standard practice is 10–20% overlap of chunk size.
20
What is the difference between PersistentClient and EphemeralClient in ChromaDB? Medium
EphemeralClient (in-memory): Data lives only in RAM. Fastest, but all vectors are lost on server restart. Good for testing only.

PersistentClient (disk-backed): Vectors are written to a directory on disk (our ./chroma_db/ directory). Survives server restarts. Used in this project for production-like behavior.

Production consideration: On Render's free tier, the disk is ephemeral between deploys. For true persistence, you would either use ChromaDB's cloud offering, mount a persistent volume (Render paid tier), or switch to a managed vector DB like Pinecone.
21
What is the difference between RAG and fine-tuning? Why RAG for this use case? Hard
Fine-tuning: Permanently updates model weights using training data. The model "memorizes" knowledge. Expensive, slow, requires labeled data, and the knowledge becomes stale as new filings are released.

RAG (Retrieval-Augmented Generation): Model weights stay frozen. At inference time, relevant documents are retrieved and injected into the prompt as context.

Why RAG for financial documents:
1. Dynamic knowledge: New annual reports, 10-K filings, and earnings documents are uploaded constantly. RAG updates instantly — fine-tuning would require retraining.
2. Source attribution: RAG can cite specific page numbers and document names. Fine-tuning cannot tell you where the model "learned" a fact.
3. Hallucination control: The model reasons over actual document text, not memorized generalizations.
4. Cost: Fine-tuning GPT-4o costs thousands of dollars. RAG costs cents per query.
22
What is the upsert operation in ChromaDB and why is it used instead of add? Medium
collection.add() fails with an error if a document ID already exists.
collection.upsert() inserts if new, updates if the ID already exists — idempotent.

In this project, each chunk gets a deterministic ID based on MD5 hash of {collection_name}-{page}-{chunk_index}. If the user re-uploads the same PDF, upsert silently overwrites existing chunks rather than throwing a duplicate key error. This makes the upload endpoint safe to call multiple times.

How would you evaluate RAG quality? What metrics would you track? Hard
Key RAG evaluation metrics:
Retrieval quality:
• Recall@k: Are the relevant chunks in the top-k results?
• MRR (Mean Reciprocal Rank): How high up is the first relevant result?
• Cosine distance: Lower = more semantically similar (already returned by ChromaDB)

Generation quality (RAGAS framework):
• Faithfulness: Does the LLM answer only use retrieved context, or hallucinate?
• Answer Relevancy: Is the generated answer actually relevant to the question?
• Context Precision: How much of the retrieved context is actually useful?

In production, I would integrate the RAGAS library and run automated evals against a golden dataset of question-answer pairs from known financial documents.

What is the embedding model used and why text-embedding-3-small vs large? Medium
text-embedding-3-small: 1536-dimensional vectors, $0.02/million tokens
text-embedding-3-large: 3072-dimensional vectors, $0.13/million tokens (6.5× more expensive)

For financial text retrieval, small achieves 98%+ of large's performance on most semantic search benchmarks. The quality difference is negligible for structured financial language (which is much simpler to embed than nuanced literary text). Cost savings are significant when indexing hundreds of PDF pages.
D. MCP — Model Context Protocol 7 Questions
25
What is MCP and why is it significant for AI applications in 2024–2025? Medium
MCP (Model Context Protocol) is an open protocol introduced by Anthropic in late 2024 that standardizes how AI models request external data and tools. It defines a structured interface: the model declares what tools it needs, and a server exposes them in a consistent format.

Significance:
• Interoperability: Any MCP-compatible LLM (Claude, GPT, Gemini) can use any MCP-compatible tool server without custom integration code
• Security: Tools are declared with typed schemas — the model can only call tools it's been given, in defined ways
• Rapidly adopted: VS Code, Cursor, Claude Desktop all support MCP. It's becoming the "USB-C for AI tool integrations"
• Auditability: Every tool call goes through a defined protocol endpoint, making agent behavior inspectable and loggable
26
What 7 tools does your MCP server expose? How do agents call them? Easy
The platform has two MCP implementations:

1. Internal Dispatcher (mcp_server/dispatcher.py) — used by all 4 agents at runtime. Every data fetch goes through call_mcp_tool(tool_name, params) which logs tool name, params, result summary, and timestamp. Tools:
1. get_stock_data — OHLCV price data for a ticker
2. get_financial_metrics — D/E, ROE, current ratio, beta, P/E
3. get_news_sentiment — headlines with sentiment scores
4. get_regulatory_rules — Basel III, AML, SOX, GDPR frameworks
5. hybrid_rag_search — BM25 + dense vector search over ChromaDB
6. rerank_chunks — GPT batch relevance scoring of retrieved chunks
7. rag_query — standard dense-only ChromaDB search (fallback)

2. FastMCP SDK Server (mcp_server/mcp_sdk_server.py) — uses the official mcp Python SDK to create a proper stdio/SSE MCP server. Runnable standalone: python -m mcp_server.mcp_sdk_server. Connectable by Claude Desktop, Cursor, or any MCP client via claude_desktop_config.json.
26a
What is FastMCP and how does it differ from the raw MCP SDK? Medium
Raw MCP SDK: Requires manually defining tool schemas, handling transport (stdio/SSE), and managing server lifecycle. Verbose boilerplate for each tool.

FastMCP is the high-level wrapper in the mcp package that provides:
• Decorator-based registration: @mcp.tool() on any Python function — type hints and docstring become the tool schema automatically
• Zero transport boilerplate: mcp.run() handles stdio/SSE negotiation
• Automatic type coercion: JSON params are cast to function argument types

Example from this project:
@mcp.tool()
def hybrid_rag_search_tool(collection: str, query: str, n_results: int = 5) -> dict:
"""Hybrid BM25 + ChromaDB dense vector search over financial documents."""
FastMCP auto-generates the JSON schema from the type hints and docstring.
27
How is MCP different from OpenAI Function Calling / Tool Use? Hard
OpenAI Function Calling / Tool Use:
• Defined per-model-call: tools are specified in the API request payload
• Tightly coupled to one LLM provider's format
• The LLM decides which tool to call and the host app handles execution

MCP:
• Defines a standalone server that any LLM can connect to
• Provider-agnostic: the same MCP server works with Claude, GPT-4o, Gemini
• Tools are "published" by the server and "discovered" by the client at connection time
• Cleaner separation: tool servers can be deployed independently

Think of it as: Function Calling = tools baked into one API call. MCP = a separate microservice that any model can plug into.

How would you secure the MCP server in production? Hard
Current state: MCP endpoints are accessible to any authenticated user (JWT required via FastAPI dependency).

Production hardening:
1. Agent-scoped tokens: Issue separate JWT tokens for agent-to-MCP communication, separate from user tokens
2. Rate limiting: Add per-tool rate limits (e.g., max 100 RAG queries/minute per user) via FastAPI middleware

The GET /mcp/tools endpoint returns a manifest. Why is a manifest important? Medium
The tools manifest is the machine-readable catalog of what the MCP server can do. It enables:

1. Tool discovery: An LLM or orchestrator can query the manifest at startup to know what tools are available — no hardcoding
2. Schema validation: The manifest defines parameter types, enabling the caller to validate requests before sending
3. Auto-documentation: Frontend dev tools can read the manifest and build a UI showing available tools
4. Versioning: Adding a version field to the manifest lets consumers know when the interface changes

This is analogous to OpenAPI's /openapi.json schema — a self-describing interface contract.
E. Backend / FastAPI / Security 9 Questions
30
Walk me through the JWT authentication flow — from registration to a protected API call. Medium
Registration: POST /api/auth/register with email/username/password. Password hashed with bcrypt (10 rounds). User stored in SQLite. JWT issued immediately.

Login: POST /api/auth/login with OAuth2PasswordRequestForm. Verify password with passlib.verify(). If valid, issue JWT: {"sub": email, "exp": now + 30min}, signed with HS256 using SECRET_KEY.

Protected request: Frontend includes Authorization: Bearer {token} header. FastAPI's OAuth2PasswordBearer dependency extracts the token. get_current_user decodes it with python-jose, validates signature and expiry, queries SQLite for the user, returns it as a dependency injection.

If token is invalid/expired → 401 Unauthorized. Frontend Axios interceptor catches 401 and redirects to /login.
31
Why bcrypt for password hashing? What makes it better than SHA-256? Medium
SHA-256 for passwords: Fast — designed for speed. An attacker can compute billions of SHA-256 hashes per second using a GPU. Once a database is breached, passwords crack in minutes.

bcrypt:
• Adaptive cost factor: The 10 rounds (cost factor) makes it ~100ms per hash. That's a user-acceptable login delay, but catastrophic for attackers (10 million attempts would take ~10 million × 100ms)
• Built-in salt: bcrypt automatically generates a unique 22-character salt per password, making rainbow tables useless
• Adjustable: As hardware gets faster, you can increase the cost factor (10 → 12 → 14) to maintain security

What does the check_same_thread=False flag in SQLite config do? Hard
SQLite's default safety mechanism prevents the same connection from being used across multiple threads. FastAPI is async and runs request handlers in a thread pool, meaning multiple requests may try to use the same SQLAlchemy connection object.

connect_args={"check_same_thread": False} disables this check, allowing the SQLAlchemy engine to safely share connections across threads via its built-in connection pool (which handles thread safety correctly internally).

This is safe because SQLAlchemy's SessionLocal creates a new session per request via the get_db() dependency — sessions are not shared across requests.

How does the conversational risk chat work? Medium
After an analysis completes, users can chat with the risk report — asking follow-up questions, requesting explanations, or exploring specific findings conversationally.

Architecture:
• Context injection: The full analysis result (all agent outputs, aggregated scores, debate results, guardrails data) is injected as the system prompt for the chat LLM call. This gives the model complete context without needing RAG over its own output.

API endpoints:
• POST /api/chat/message — send a user message, receive AI response (with full analysis context)
• GET /api/chat/history/{analysis_id} — retrieve previous chat messages for an analysis

Why Zustand over Redux for state management? Easy
Redux requires: store configuration, reducers, actions, action creators, selectors, and often middleware (Redux Thunk or Saga). For a single auth state with 3 fields, this is massive overkill.

Zustand: one 15-line file with create(). Access state with a hook: const { token, setAuth } = useAuthStore(). Built-in persist middleware for localStorage. No Provider wrapper needed.

Rule of thumb: Use Zustand for 1–3 global states. Use Redux when you need time-travel debugging, complex derived state, or a large team working on shared state simultaneously.

What are the bottlenecks at scale and how would you address them? Hard
Bottleneck 1 — LLM latency (20–30s per analysis): Addressed with SSE (Server-Sent Events) streaming — users now see results as each agent completes in real time, rather than waiting for all agents to finish. Further optimization: parallel agent execution could reduce total time from ~20s to ~5s.
Bottleneck 2 — OpenAI rate limits: Implement a queue (Celery + Redis) so analyses run in the background. Add retry with exponential backoff.
Bottleneck 3 — SQLite concurrency: SQLite is single-writer. Migrate to PostgreSQL (1-line env change with SQLAlchemy).
Bottleneck 4 — ChromaDB disk persistence on Render: Migrate to Pinecone or ChromaDB's hosted cloud for true persistence across deploys.
Bottleneck 5 — Cold starts on Render free tier: Upgrade to Render paid tier, or add a keep-alive ping (cron job hitting /api/health every 14 minutes).

How does real-time streaming of agent results work in the platform? Hard
The platform uses Server-Sent Events (SSE) via FastAPI's StreamingResponse with text/event-stream content type. As each LangGraph agent completes, an event is pushed to the frontend in real time.

Why POST-based SSE (not EventSource): The browser's native EventSource API only supports GET requests. Our analysis requires a POST body (company name, ticker, sector, collection). So the frontend uses fetch() with ReadableStream to consume the SSE stream from a POST endpoint.

Event types streamed:
• agent_start — an agent has begun processing (triggers loading indicator)
• agent_complete — an agent finished, includes its result payload
• guardrails_complete — hallucination check finished for an agent, includes confidence score
• debate_start — debate phase (Devil's Advocate + Judge) has begun
• analysis_complete — final aggregated result with all scores

# Backend (FastAPI) async def event_generator(request_data): for agent_name in ["market_risk", "sentiment", "financial_report", "regulatory"]: yield f"event: agent_start\ndata: {json.dumps({'agent': agent_name})}\n\n" result = await run_agent(agent_name, state) yield f"event: agent_complete\ndata: {json.dumps(result)}\n\n" yield f"event: analysis_complete\ndata: {json.dumps(final)}\n\n" return StreamingResponse(event_generator(data), media_type="text/event-stream")
// Frontend (React) — POST-based SSE with fetch + ReadableStream const response = await fetch('/api/analysis/stream', { method: 'POST', body: JSON.stringify(data) }) const reader = response.body.getReader() const decoder = new TextDecoder() while (true) { const { done, value } = await reader.read() if (done) break const text = decoder.decode(value) // Parse SSE events and update UI progressively }
SSE was chosen over WebSockets because the data flow is unidirectional (server → client). POST-based SSE via fetch() solves the EventSource GET-only limitation while keeping HTTP simplicity.

How does SSE streaming work end-to-end in the platform? Walk through the full flow. Hard
End-to-end SSE flow:

1. Frontend initiates: User clicks "Analyze" → React sends a POST request to /api/analysis/stream with {company, ticker, sector, collection_name}. Uses fetch() (not EventSource) because POST body is required.

2. Backend creates generator: FastAPI endpoint returns a StreamingResponse wrapping an async generator. The generator walks the LangGraph nodes one by one, yielding SSE-formatted events after each step.

3. Event format: Each event follows the SSE specification:
event: agent_complete data: {"agent": "market_risk", "score": 42, "level": "MEDIUM", ...} event: guardrails_complete data: {"agent": "market_risk", "confidence": 87, "issues": []} event: debate_start data: {"message": "Devil's Advocate analyzing findings..."} event: analysis_complete data: {"overall_score": 58.4, "risk_level": "HIGH", ...}
4. Frontend reads stream: response.body.getReader() returns a ReadableStream reader. The React component reads chunks in a while(true) loop, decodes with TextDecoder, parses SSE event/data lines, and dispatches state updates per event type.

5. Progressive UI update: Each agent_complete event triggers the corresponding agent card to animate from "loading" to "complete" with its score. The overall gauge updates incrementally. Guardrails confidence badges appear as each validation completes.

Why not WebSockets: SSE is HTTP-native (works through proxies, load balancers, CDNs without upgrade negotiation), auto-reconnects on network hiccups, and the data flow is purely server → client. WebSockets would add bidirectional complexity for a unidirectional use case.
The POST-based SSE pattern (fetch + ReadableStream) is increasingly common in AI applications — it's the same approach used by ChatGPT's streaming responses.
